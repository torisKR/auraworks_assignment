# 면접 설명 준비

## 1분 설명

“제공된 스토어 화면을 Next.js App Router와 TypeScript로 구현했습니다. 교재 12개는 Supabase PostgreSQL에 저장하고 요구사항에 맞게 브라우저에서 조회합니다. 화면, 요청 생명주기, DB 접근, 타입을 분리해서 디자인 변경과 데이터 조회 변경이 서로 영향을 적게 주도록 했습니다. 공개 키를 사용하는 대신 DB에서 RLS와 SELECT 전용 권한을 설정했습니다. 검색·필터 핵심 로직은 순수 함수로 분리해 테스트했고, 조회 실패와 빈 결과도 사용자에게 명확하게 보여 줍니다.”

이 문장은 코드·단위 테스트·DB 권한 검증까지 설명합니다. 실제 배포 URL, 모바일 렌더링, 브라우저 네트워크 확인 결과는 검증이 끝난 범위만 덧붙입니다.

## 자주 나올 질문

### Next.js를 쓰면서 왜 CSR인가요?

과제에서 교재 목록 CSR을 요구했습니다. 정적인 페이지 구조와 메타데이터는 App Router를 사용하고, 교재는 `useTextbooks`의 effect에서 조회합니다. 공개 목록의 SEO가 주요 요구사항으로 바뀌면 Server Component나 ISR을 검토할 수 있습니다. 현재 데이터 흐름을 바꾸는 결정은 요구사항을 먼저 확인합니다.

### 왜 API Route를 거치지 않았나요?

공개 더미 교재를 읽는 기능이고 Supabase Data API와 RLS가 있습니다. 동일한 SELECT를 전달하는 서버 프록시를 추가하면 요청 경로와 관리 코드만 늘어납니다. 관리자 작업, 비밀 키, 가격 검증, 결제처럼 서버 신뢰가 필요한 기능은 서버 경로로 분리해야 합니다.

### 공개 키가 노출되어도 괜찮나요?

publishable 키는 공개 클라이언트용입니다. 접근 권한은 DB에서 제한합니다. 교재 테이블은 RLS를 켜고 읽기 정책만 만들었습니다. `anon` 역할로 12개 조회가 되는 것과 INSERT/UPDATE/DELETE 권한이 없다는 것을 SQL로 확인했습니다. 개인 데이터가 추가되면 테이블과 소유권 정책을 별도로 설계합니다.

### 폴더를 왜 이렇게 나눴나요?

컴포넌트가 쿼리 문자열이나 DB 테이블명을 알지 않도록 했습니다. 훅은 요청 상태를, `textbooks.ts`는 조회 계약을, `catalog.ts`는 검색 규칙을 담당합니다. 예를 들어 서버 페이지네이션을 추가할 때 카드 디자인은 바꿀 필요가 없습니다. 파일을 역할별로 나누되 현재 없는 도메인의 빈 폴더는 만들지 않았습니다.

### 상태가 세 개뿐인데 union을 쓴 이유는요?

`loading`, `success`, `error`를 타입으로 구분하면 성공 전에 교재를 읽거나 오류가 없는데 메시지를 읽는 실수를 TypeScript가 잡습니다. 여러 boolean보다 가능한 상태를 이해하기 쉽습니다. 빈 결과는 요청이 성공한 뒤 배열 길이가 0인 경우이므로 별도 비동기 상태로 만들지 않았습니다.

### 검색은 왜 클라이언트에서 하나요?

12개 더미 데이터는 한 번 조회한 뒤 즉시 검색하는 방식이 단순합니다. 제목·과목을 검색하고 카테고리 필터와 교집합을 구합니다. 데이터가 커지면 서버 검색과 페이지네이션을 적용해 전송량을 줄이고 인덱스를 확인합니다.

### 렌더링 최적화는 어떤 것을 했나요?

이미지 크기를 명시해 레이아웃 이동을 줄이고 `next/image`와 `sizes`로 응답 크기에 맞는 이미지를 선택합니다. 첫 배너는 우선 로드합니다. 12개 필터 연산은 비용이 작아서 모든 함수에 memoization을 적용하지 않았습니다. 실제 병목이 확인되면 프로파일링 결과를 바탕으로 개선합니다.

### 요청 중 화면을 나가거나 다시 시도하면요?

effect 정리 시 AbortController로 요청을 취소합니다. 취소된 요청은 상태를 갱신하지 않습니다. 재시도는 새 요청 버전을 만들어 이전 effect를 정리하고 다시 조회합니다. React Strict Mode의 개발용 effect 재실행에서도 같은 취소 처리가 적용됩니다.

### 테스트가 보장하는 범위는 무엇인가요?

6개 단위 테스트는 검색·필터 조합, 공백·대소문자·한글 정규화, 빈 목록·결과, 입력을 바꾸지 않는 동작, 가격 표시를 검증합니다. lint, strict typecheck, 프로덕션 build도 실행합니다. DB에서는 익명 SELECT와 권한을 검증합니다. 이것만으로 실제 브라우저 UI와 배포 상태를 검증했다고 말하지 않습니다.

### 원본과 다르게 판단한 부분은 무엇인가요?

작은 화면에서는 3열·2열로 변경하고 키보드 포커스와 로딩·오류 상태를 추가했습니다. 제공 배너를 재사용했기 때문에 이미지 안의 텍스트와 `1/5` 표시는 artwork입니다. 원본의 정가·판매가·5% 배지는 수학적으로 일치하지 않지만 화면 재현 요구에 따라 그대로 표시하고 문서에 기록했습니다.

### 실제 결제를 붙인다면요?

브라우저 장바구니 가격으로 결제 금액을 확정하지 않습니다. 서버가 DB 교재 가격을 읽어 주문을 만들고, 결제 결과는 webhook 검증을 거쳐 반영합니다. 사용자별 주문 조회 권한, 상태 전이, 중복 요청, 트랜잭션을 고려합니다. 현재 구현은 임시 장바구니까지입니다.

### AI를 어떻게 사용했나요?

화면 분석, 구현 초안, 반복 검증에 AI를 활용했습니다. 설명할 때는 생성된 코드의 책임 분리, CSR 데이터 흐름, RLS 정책, 테스트의 실제 보장 범위를 직접 이해하고 이야기해야 합니다. 배포나 검증이 실패한 부분도 완료한 것처럼 설명하지 않습니다.

## 시연 순서

1. 페이지 진입 후 스켈레톤이 교재 목록으로 바뀌는 것을 보여 줍니다.
2. DevTools Network에서 `textbooks?select=...&order=display_order.asc` 요청을 확인합니다.
3. 패스·단품 필터를 바꾸고 과목 검색을 조합합니다.
4. 없는 검색어로 빈 결과와 초기화를 보여 줍니다.
5. 상품 상세와 장바구니 담기·삭제를 시연합니다.
6. 작은 화면에서 2열 레이아웃과 키보드 모달 닫기를 보여 줍니다.
7. 코드의 `useTextbooks → fetchTextbooks → Supabase` 경로와 migration의 RLS 정책을 설명합니다.
8. Git 기록에서 설정·UI·DB·테스트·리팩터링·문서 변경이 나뉜 것을 보여 줍니다.
